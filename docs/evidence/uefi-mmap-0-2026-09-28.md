# UEFI-MMAP-0 — OVMF memory map vs ForthOS's fixed layout (read-only probe, 2026-09-28)

**Asked for by** amendment (d) of `uefi-2-prereg-2026-09-28.md`. It runs
**before any UEFI-2 code**, and nothing is designed around its result
here.

## Method

- **The run.** `qemu-system-x86_64 -M q35` with `OVMF_CODE_4M.fd`
  (OVMF 2024.02, no CSM), a scratch copy of `OVMF_VARS_4M.fd`, no disk,
  and serial over TCP. The probe typed ESC (to skip `startup.nsh`) and
  then `memmap`.
- **Two memory sizes**, to see whether the low map depends on RAM:
  - `-m 512M`, the UEFI-1 fixture: `uefi-mmap-0-ovmf-512M-2026-09-28.log`,
    128 entries;
  - `-m 2G`: `uefi-mmap-0-ovmf-2G-2026-09-28.log`, 128 entries.
- **Classification rule (owner's).** `Available` (Conventional) and
  `BS_Code` / `BS_Data` (BootServices) are **free** after
  ExitBootServices. Any other type is a **collision**, and so is any
  address in a window that no entry covers.

## Result: no collision in QEMU/OVMF, at either size

| window (ForthOS use) | 512M | 2G |
|---|---|---|
| 0x7C00–0x9FFFF: boot sector image, kernel at 0x7E00, data stack below 0x7C00, return stack to 0x28000, variables at 0x28000, IDT at 0x29400 | `Available 0x1000-0x9FFFF` covers it all: **CLEAR** | the same: **CLEAR** |
| 0x30000–0x7FFFF: dictionary, `DICT_LIMIT` 0x80000 exclusive | inside the same `Available` range: **CLEAR** | **CLEAR** |
| 0x100000–0x3FFFFF: physical pool, `PHYS-TOP` 0x400000 exclusive | `Available 0x100000-0x7FFFFF`: **CLEAR** | **CLEAR** |

**Nearest non-free memory** (both sizes):
- **`ACPI_NVS` at 0x800000**, 4 MiB above the pool's top.
- **Page 0** (0x0–0xFFF) is `BS_Code`, which is free after exit.
- **0xA0000–0xFFFFF is absent from the map** (the legacy VGA/ROM hole).
  No ForthOS window touches it.

## What this does NOT establish (named, not measured)

1. **The map changes before GRUB boots the kernel.** This is the map
   while the EFI **shell** runs. GRUB's own allocations
   (`LoaderCode`/`LoaderData`, its relocator's staging chunks) come
   later. The map that counts is the one GRUB hands to the kernel.
   UEFI-3 reads the multiboot2 memory-map tag and reports collisions
   against it, as the staged plan says.
2. **The ASUS is not QEMU.** Firmware on iron (Aptio) can place
   Runtime, ACPI or Reserved regions anywhere. The iron map needs its
   own probe. The same `memmap` from an EFI shell on the ASUS, or the
   UEFI-3 kernel's own report, is owed before UEFI-5.
3. **Other QEMU machine types and sizes** (`-M pc`, smaller RAM) were not
   probed.

## GRUB 2.12: does the x86_64-efi multiboot2 loader accept load address 0x7E00?

**Read from the GRUB 2.12 source** (`git.savannah.gnu.org`, tag
`grub-2.12`, fetched 2026-09-28, sha256 prefixes below). The source is
**not** in any repo; only line numbers are cited.
- `grub-core/loader/multiboot_mbi2.c` 47bcf1012a59ae50
- `grub-core/loader/multiboot.c` 7a5987093548f39f
- `grub-core/loader/multiboot_elfxx.c` 92f65f99f06dfa20
- `grub-core/lib/relocator.c` 3195929f118406c2
- `grub-core/lib/i386/relocator.c` ea43f9552880a4b9
- `include/multiboot2.h` 9ab9ebe4879a7f4d

**Yes, by the source, as read.**

1. **The allocation.** A non-relocatable image is placed at its fixed
   target:
   - with the address tag, `grub_relocator_alloc_chunk_addr(…, load_addr,
     code_size)` (`multiboot_mbi2.c:310-311`);
   - as an ELF, per segment at `p_paddr` (`multiboot_elfxx.c:176-177`).

   The relocatable tag, by contrast, goes to
   `grub_relocator_alloc_chunk_align_safe` with min/max
   (`multiboot_mbi2.c:230-234, 304-307`).
2. **No floor below 1 MiB.** `grub_relocator_alloc_chunk_addr`
   (`relocator.c:1231-1306`) refuses only in two cases:
   - an overflowing target (l.1238-1239);
   - a target that overlaps another chunk (l.1243-1246).

   `adjust_limits` starts `min_addr` at 0 (l.1214). For an x86
   **target below 0x100000** there is explicit handling (l.1260-1268):
   the payload is **staged** high (`chunk->src`), and the move to
   `target` is deferred.
3. **The move happens after ExitBootServices.** In `grub_multiboot_boot`:
   - `make_mbi` runs first (`multiboot.c:186`). For a kernel without the
     EFI-boot-services tag (`keep_bs == 0`), it calls
     **`grub_efi_finish_boot_services`** (`multiboot_mbi2.c:943-948`) and
     records the final EFI map in the MBI.
   - Only then does `normal_boot`, i.e. `grub_relocator32_boot`
     (`multiboot.c:191-192`, 161-165), move the chunks to their targets
     and jump.

**The caveat from the same reading.** `grub_relocator_alloc_chunk_addr`
does **not** check the target against the firmware memory map; there is
no such check in l.1231-1306. A target inside a Runtime or ACPI region
would be overwritten silently. So **the kernel's own check of the
multiboot2 memory map (UEFI-3) is the only guard** against a collision
on iron.

- **Reasoned from reading the code, not run.** GRUB was not actually
  booted with a 0x7E00 multiboot2 image here. UEFI-3's red → XPASS is
  the run.
- **Not audited:** other GRUB paths (preboot hooks, the EFI mmap
  iteration used for staging at `relocator.c:1448-1452`).
